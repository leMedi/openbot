# OpenBot Project Context

This document is the authoritative context for the OpenBot MVP. It describes
the product model, durable data boundaries, runtime behavior, and intentional
deferrals. The canonical database definition is
`packages/db/src/schema.ts`; this document explains that model but does not
duplicate its SQL.

## Product Model

OpenBot is a server installed on a remote machine and a web or mobile client
that connects to it through APIs. The server owns all agent execution and
durable domain data. Clients never access the database or managed files
directly.

The installation has one user and no tenant or ACL model. The user can create
multiple long-lived agents. Each agent has its own identity, conversations,
memory, turn queue, checkpoints, and runtime. Agents can send direct messages
to one another and participate in groups.

An agent has two distinct forms of state:

- Persistent state: identity, stable defaults, conversations, messages,
  checkpoints, memory, MCP access, and historical turns.
- Runtime state: live runners, abort controllers, open connections, discovered
  tools, active streams, and in-memory scheduler state.

Runtime-only objects are not serialized. Durable queue records and checkpoints
provide the boundary needed to resume work after a restart.

## Runtime Architecture

```text
Client
  |
  | authenticated server API
  v
OpenBot server on remote machine
  |
  +-- local libSQL database
  +-- managed file directory
  +-- agent and group schedulers
  +-- inference and tool execution
  +-- MCP connections and credentials
```

The database is always a local file and is accessible only to the server.
Client operations go through server APIs. The current database location is
`$OPENBOT_DATA_DIR/store.db`, with relative data-directory values resolved
from the workspace root.

At startup the server:

1. Opens the local libSQL database.
2. Enables SQLite foreign-key enforcement.
3. Requests WAL journal mode.
4. Applies committed Drizzle migrations.
5. Stops startup if migration fails.
6. Resets interrupted `running` turns to `queued` and increments their attempt
   count.

## Durable Storage Scope

One database stores all MVP domain data for all agents and groups. Files such
as avatars and attachments remain in an application-owned directory; the
database stores their relative paths and serving metadata.

The MVP schema has these tables:

| Table | Responsibility |
| --- | --- |
| `managed_files` | Metadata for application-owned files on disk. |
| `agents` | Agent identity, appearance, stable defaults, and UI settings. |
| `groups` | Group identity and versioned JSON membership. |
| `conversations` | Agent conversations and each group's shared conversation. |
| `conversation_checkpoints` | Immutable, versioned model/runtime snapshots. |
| `turns` | Durable queue items and historical execution records. |
| `conversation_messages` | Ordered UI transcript, tool records, and delivery projections. |
| `memory_items` | Shared-user and agent-scoped durable memory. |
| `mcp_servers` | Global MCP server definitions. |
| `mcp_accounts` | API-key or OAuth accounts for MCP servers. |
| `agent_mcp_accounts` | Explicit agent access to MCP accounts. |

All IDs are generated by the server as prefixed, cryptographically random text
values. Timestamps are Unix epoch milliseconds stored as integers.

## Agents

An `agents` row contains:

- Name and description.
- Optional avatar managed-file reference.
- Default mode and model.
- Approval mode.
- Notification and sidebar visibility settings.
- Creation and update timestamps.

The effective tool list is not an agent column. It is derived for each turn
from runtime capabilities, MCP discovery, permissions, and execution context.
Historical effective tools and permissions are snapshotted on the turn.

Subagents are not persistent agent rows in the MVP. Their definitions are
hardcoded inference capabilities supplied by the TanStack AI integration, much
like tools. Subagent calls, results, and resumable state are captured by
conversation messages and checkpoints.

## Groups

Groups are separate from agents. A group has a name, description, optional
avatar, timestamps, and versioned `members_json`.

The current membership shape is:

```json
{
  "version": 1,
  "members": [
    { "type": "agent", "agentId": "agt_example" }
  ]
}
```

Discriminated member objects allow external member types to be introduced
later. Because member IDs are inside JSON, SQLite cannot enforce membership
foreign keys or cascade into the array. Group services must validate member
IDs and remove an agent from every group in the same transaction that deletes
the agent.

Each group has exactly one shared conversation, represented by a unique
`conversations.owner_group_id`. The group row does not duplicate the
conversation ID.

### Group Execution

When a user posts in a group:

1. The message is appended to the group's shared conversation.
2. One group-targeted turn is queued.
3. The group orchestrator reads current room history.
4. It selects members from mentions and recent room context.
5. Selected members receive sequential, agent-targeted child turns.
6. Member `SendMessage` output is appended only to the group transcript.
7. The orchestrator may begin another bounded round.

Child turns retain `parent_turn_id`, orchestration round, and position within
the round. Group scheduling bounds are runtime configuration, not database
configuration.

## Conversations

Agents may own multiple conversations. A conversation is owned by exactly one
agent or one group, enforced by nullable owner foreign keys and an XOR check.
There is no participants table in the MVP.

A conversation stores:

- Optional title.
- Current checkpoint pointer.
- Current plan URI.
- Next transcript sequence number.
- Last-read sequence, manual-unread state, and introduction state.
- Optional origin and purpose metadata.
- Creation and update timestamps.

The client remembers its last selected conversation in `localStorage`. This
is client-local navigation preference, not server domain state.

Clearing a conversation deletes that conversation and its dependent messages,
turns, and checkpoints, then creates a fresh conversation. Managed files are
deleted only after no remaining avatar or message references them.

## Conversation Messages

`conversation_messages` is the unified UI transcript. There is no separate
canonical messages table. Rows can represent:

- User and assistant messages.
- Direct agent inbound and outbound messages.
- Group messages.
- Tool calls and tool results.
- Status, system, and other display events.

Every row has a conversation sequence number. Stable message kinds, roles, and
directions are constrained by SQLite. Reply, thread-root, and branch-parent
references use composite foreign keys so they cannot cross conversation
boundaries. A message's turn reference is constrained to the same
conversation.

Type-specific data lives in versioned `payload_json`. Reactions and attachments
are also versioned JSON columns. Their detailed shapes are validated by Zod in
`packages/db/src/json-schemas.ts`, while SQLite ensures stored JSON is
parseable.

Reaction state has toggle semantics: applying a missing actor/reaction pair
adds it, while applying the same pair again removes it. Both actor IDs being
null identifies the single local user. Reaction read/modify/write operations
must be transactional.

Attachments contain managed-file IDs, positions, and metadata. SQLite cannot
enforce foreign keys inside attachment JSON, so the message and file services
must validate references and account for them during cleanup.

### Direct Agent Messages

A direct message is copied into both agents' private transcripts. The sender
gets an outbound row and the recipient gets an inbound row. Both rows share a
`delivery_id`.

Acceptance is one database transaction that:

1. Appends the sender transcript copy.
2. Appends the recipient transcript copy.
3. Creates the recipient's queued turn.

This transaction is the durable inbox boundary. The runtime may maintain
in-memory queues for speed, but they are not authoritative. The recipient
turn's status records whether processing has completed.

## Turns and Scheduling

A turn is both a durable scheduler item and a historical execution record.
There is no separate runs table.

A turn targets exactly one agent or one group. It stores:

- Conversation and optional parent turn.
- Queue lane: user, agent, or background.
- Extensible source and mode values.
- Lifecycle status: queued, running, waiting, succeeded, failed, or cancelled.
- Model provider and model ID.
- Request and idempotency identifiers.
- Versioned effective-tool, permission, and runtime-context snapshots.
- Optional waiting and error state.
- Attempt count and execution timestamps.
- Group orchestration round and position where applicable.

The scheduler permits one active turn per target and prioritizes lanes in this
order:

```text
user > agent > background
```

That exclusivity is enforced by the server scheduler, not a database
constraint. A turn waiting for user input persists the prompt, options,
originating tool call, and resume data in `waiting_state_json`.

If the server restarts while a turn is running, startup resets it to queued and
increments `attempt_count`. Tool side effects still require their own
idempotency controls because the server cannot guarantee exactly-once external
execution.

## Checkpoints

Runtime conversation state and the UI transcript are deliberately separate.
A transcript is optimized for display and interaction; a checkpoint contains
the full model-facing state needed to resume execution.

Checkpoint state may include prompts, turns, tool calls and results, todos,
summaries, pending operations, workspace references, subagent state, and
frozen memory/profile prompt snapshots.

`conversation_checkpoints` stores immutable JSON snapshots with:

- Conversation and optional parent checkpoint.
- Positive schema version.
- State JSON.
- Serialized byte size.
- SHA-256 content hash.
- Creation timestamp.

The conversation points to its current checkpoint. Checkpoints are immutable
through the TypeScript data API and all versions are retained until their
conversation is deleted. Garbage collection is deferred.

## Memory

Memory is stored as mutable individual items rather than Markdown files. An
item has user or agent scope, profile/log/note kind, content, author
provenance, versioned metadata, and timestamps.

User memory is shared across agents while retaining the author agent ID. Agent
memory has a required subject agent. Agents may update or immediately forget
memory items. Project memory is deferred.

## Managed Files

`managed_files` stores a stable ID, application-relative path, original name,
media type, byte size, and creation timestamp. Paths must resolve within the
application-owned managed-file directory. APIs serve files to clients after
authorization and path validation.

Agent and group avatars use normal foreign keys. Message attachment IDs live
inside versioned JSON and are application-validated. A file may be reused by
multiple records.

Deletion intentionally has no durable outbox in the MVP. The server commits
database deletion first and then attempts disk deletion. A process failure can
leave an orphaned disk file; this is an accepted MVP limitation. A maintenance
command can later scan for and remove unreferenced files.

## MCP

MCP server definitions and accounts are global to the single user. Agents gain
explicit access through `agent_mcp_accounts`. Effective MCP tools are still
discovered for every turn and are never inferred from old turn snapshots.

An MCP server stores its key, name, transport, versioned configuration,
enabled state, and timestamps. A server may have multiple labeled accounts.
Accounts use either API-key or OAuth authentication.

Credential JSON is versioned and validated according to authentication type.
OAuth credentials can include access token, refresh token, token type, scopes,
and expiry. OAuth state and PKCE verifier are kept only in memory; an in-flight
authorization fails if the server restarts.

MCP credentials are plaintext in the MVP database. This is a consciously
accepted temporary security limitation. Credential rows must never be
returned from normal APIs, logged, written into transcripts or checkpoints,
or included in prompts. Encryption and an external secret vault are deferred.

## Deletion and Integrity

Database deletion is immediate and uses cascading foreign keys for relational
children. APIs must require appropriate user confirmation before destructive
operations.

Some invariants are necessarily application-owned:

- Group member IDs and message attachment file IDs are stored inside JSON.
- Current checkpoints and parent links must belong to the same conversation.
- Group creation must create its one shared conversation.
- Sequence allocation atomically increments `conversations.next_sequence_no`.
- Checkpoint rows are never updated after insertion.
- Reaction toggles use transactional read/modify/write.
- Direct-message transcript copies and recipient turn are inserted atomically.
- Plaintext MCP credentials never cross safe service boundaries.

Detailed JSON shape and version validation is owned by Zod. SQLite check
constraints enforce parseable JSON and stable relational lifecycle values.

## Deferred Capabilities

The following are explicitly outside the MVP schema:

- Projects and project memory.
- Automations, routines, notices, and run history.
- Workflows and workflow versions.
- Slack, Discord, and other communication channels.
- Tool approval and retirement rules.
- Full-text transcript and memory search.
- Durable OAuth authorization flows.
- Checkpoint garbage collection and storage limits.
- A transactional file-deletion outbox.
- Persisted subagent definitions.
- Remote libSQL or Turso operation.
- MCP credential encryption or secret-vault integration.

These features should receive schema tables only when their runtime and API
behavior is being implemented.

## Implementation Status

The schema, generated initial migration, startup migration path, JSON contracts,
ID helper, agent profile and avatar services, conversation navigation, the
transcript repository, the durable turn queue with restart recovery and
persisted waiting-turn resume, the checkpoint repository, durable user and
agent memory, and single-agent turn execution with streamed visible output are
implemented. User message acceptance is idempotent by request ID or stable
idempotency key. Per-target claims enforce one active turn and
`user > agent > background` priority. A turn is executed by the server-side runner
(`apps/app/src/server/turn-runner.ts`): it claims the queued turn, snapshots
the effective model/tools/permissions/runtime context, streams one
OpenAI-compatible chat completion, appends the assistant transcript row,
writes the next immutable checkpoint, and marks the turn terminal. Visible
output reaches clients over a per-turn SSE route; execution never depends on
a connected client.

Group shared rooms are implemented: group identity, avatar, and versioned
membership services, one shared conversation created with the group, a
group-targeted turn queued per user post, and a group orchestrator that
selects one member (mention match, else first member) and queues one
agent-targeted child turn with parent/round/position linkage. The member's
answer carries `sender_agent_id` in the shared transcript only. Selection
from recent room context, multi-member sequential rounds, and further bounded
rounds remain future work.

Remaining implementation slices are:

1. Tool execution that can originate the implemented waiting-turn interaction.
2. Transactional direct agent delivery.
3. Group selection from room context and bounded multi-member rounds.
4. Managed attachments and file-serving APIs.
5. MCP server, account, OAuth callback, and safe credential access services.

## Source Map

- `packages/db/src/schema.ts`: canonical Drizzle table and constraint model.
- `packages/db/src/json-schemas.ts`: versioned durable JSON contracts.
- `packages/db/src/ids.ts`: prefixed server ID generation.
- `packages/db/src/client.ts`: database startup (pragmas, migrations, turn recovery).
- `packages/db/src/agents.ts`: agent registry repository, including avatar operations.
- `packages/db/src/groups.ts`: group registry repository (identity, avatar,
  validated versioned membership, the one shared conversation).
- `packages/db/src/avatars.ts`: shared avatar-upload contract and validation.
- `packages/db/src/conversations.ts`: conversation repository (navigation state,
  atomic sequence allocation, clear-into-fresh-conversation).
- `packages/db/src/messages.ts`: transcript repository (ordered appends and the
  idempotent atomic user-message + queued-turn accept).
- `packages/db/src/turns.ts`: durable turn queue (target-safe priority claims,
  waiting/resume, terminal settlement, execution snapshots, and atomic group
  child-turn delegation).
- `packages/db/src/checkpoints.ts`: immutable checkpoint repository and
  current-checkpoint pointer.
- `packages/db/src/memory.ts`: scoped memory CRUD, metadata validation, and
  prompt-relevant memory selection.
- `packages/db/src/files.ts`: managed-file repository and path containment.
- `packages/db/src/index.ts`: package exports.
- `packages/db/src/env.ts`: local database, migration, and managed-file paths.
- `packages/db/drizzle/`: generated committed migrations and metadata.
- `apps/app/src/server/agents.ts`: current agent API boundary.
- `apps/app/src/server/groups.ts`: group API boundary (identity, membership,
  deletion).
- `apps/app/src/server/conversations.ts`: conversation API boundary.
- `apps/app/src/server/messages.ts`: transcript read and durable send API boundary.
- `apps/app/src/server/memory.ts`: memory inspection and mutation API boundary.
- `apps/app/src/server/prompt-assembly.ts`: agent-scoped prompt memory assembly
  and private checkpoint-epoch reuse.
- `apps/app/src/server/ai.ts`: OpenAI-compatible streaming inference client.
- `apps/app/src/server/turn-runner.ts`: turn executor, group orchestrator,
  per-target drains, and in-memory visible-output fan-out.
- `apps/app/src/routes/api.agents.$agentId.avatar.ts`: agent avatar file-serving API.
- `apps/app/src/routes/api.groups.$groupId.avatar.ts`: group avatar file-serving API.
- `apps/app/src/routes/api.turns.$turnId.stream.ts`: per-turn SSE stream of
  visible output.
- `apps/app/src/routes/index.tsx`: current agent registry UI.

Generated migrations are deployment artifacts. They do not replace
`packages/db/src/schema.ts` as the authored schema source of truth.
